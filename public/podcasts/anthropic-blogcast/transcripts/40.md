**Alex:** Welcome to Anthropic Blogcast. Today we are answering a question every developer building with Claude now has to make, which model should you actually start with.

**Jordan:** This is the new developer guide from Claude dot dev, called Which Claude model should you build with, Fable, Opus, Sonnet, or Haiku. It was published on November ninth, twenty twenty six, the same day Anthropic launched Fable five point two.

**Alex:** The lineup is bigger than it used to be. There are four generally available models. Haiku five point five is the smallest and fastest, Sonnet five point five is the fast capable middle, Opus five point five is the daily driver, and Fable five point two is the most capable model for the hardest technical work. Mythos five point two is the same underlying model as Fable without some safeguards, available only through verification programs for cybersecurity and life sciences research.

**Jordan:** So where do you start? The guide is direct. Start most work on Opus five point five, at its default effort level, medium.

**Alex:** That is why Opus is the default in Claude Code. It costs half as much per token as Fable, four dollars per million input tokens and twenty dollars per million output tokens, compared with eight dollars and forty dollars for Fable. For most coding and knowledge work, it is strong enough that you may never need to move.

**Jordan:** From there, move down to Sonnet five point five for well scoped everyday work, like a bug fix or a feature built against a clear specification. Sonnet costs two dollars per million input tokens and ten dollars per million output tokens, half the Opus price.

**Alex:** Move further down to Haiku five point five for the simplest high volume work, classification, routing, tagging, and extraction. Haiku costs just ten cents per million input tokens and fifty cents per million output tokens for prompts up to one hundred thousand tokens. Above that length the price jumps five times, so Haiku pays off most when prompts stay short. Haiku is also ideal for subagents doing side tasks for a larger model.

**Jordan:** And move up to Fable five point two only for the hardest projects, major refactors and migrations, architecture planning, deep research, and scientific or quantitative analysis. Also move up when Opus at high effort still falls short, or for long unattended runs.

**Alex:** Before you switch models at all, try adjusting effort first. Effort is the finer dial. Higher effort means the model thinks longer, calls more tools, and checks its own work more, but it also adds latency and cost.

**Jordan:** And there is a crossover worth remembering. Past high effort, one more level can cost as much as a bigger model, so test the next model up at a lower effort instead. Conversely, dropping one effort level can often get you the result you need for less.

**Alex:** A few task picks from the guide's table are worth keeping. For chat where a person is waiting, start with Sonnet at low or medium, because speed matters. For computer use and vision heavy work, use Opus at medium, because those are long loops over many screenshots. For subagents that search files, read logs, or summarize, use Haiku or Sonnet, because a wrong answer there is cheap to spot and the main model still makes the judgment calls.

**Jordan:** Now the trade off that surprised me most is cost per finished task, not cost per token. A bigger model costs more per token, but the finished job does not always cost more.

**Alex:** The examples make that concrete. On Frontier Code two point zero, Fable five point two at high scored about level with Opus five point five at max, forty five point three percent versus forty five point five percent, for roughly half the cost per task. In other testing, Opus at high beat the previous Fable at max while using half the tokens. And the hardest tasks carry most of the spend. In one twenty problem search benchmark, just two problems carried forty three percent of the total cost.

**Jordan:** Latency follows the same pattern. On S W E bench Pro, Opus at medium scored about two point five points lower than high, for about seventy percent of the cost. At low it scored about eight points lower for about a third of the cost. At extra high it gained only about one point four points, for two and a half times the cost of high.

**Alex:** Which leads to my favorite trick in the article. If you can check outcomes automatically, run everything at low effort first, and re run only the failures at high. On that same benchmark, that passed about ninety seven percent of tasks for about seventeen cents each, compared with ninety five point three percent for twenty nine cents each when everything ran at high.

**Jordan:** Self verification often beats raising effort too. Give the model a test, a build, or a script so it can check its own work. Thinking longer will never give a model knowledge it does not have. For that, you really do need to move up a model.

**Alex:** Context is the other hidden cost. Every model here has a one million token context window and a maximum output of one hundred and twenty eight thousand tokens, but large context is resent on every turn. On long runs most of that bills as cache reads, twenty cents per million tokens on Opus and Fable, and ten cents on Sonnet. A turn with one hundred and fifty thousand tokens of context costs about three cents in cache reads, while twenty thousand tokens costs about four tenths of a cent. Keep the expensive model's context lean, and let cheaper subagents do the verbose reading.

**Jordan:** That is the bridge to mixing models. In Claude Code you can set a subagent to run on Haiku or Sonnet in its definition, or set a default subagent model for the ones that do not specify one. The guide gives a log reader example that runs on Haiku, reads test output, and reports each failure with the file, the test name, and the first error line, without editing files.

**Alex:** Two cautions if you mix. First, switch at a natural break. The prompt cache belongs to the model that wrote it, so your first turn on a new model pays to rewrite the whole conversation. Run compact first, or start fresh on the A P I with a short summary. Second, thinking does not always travel. Fable reads thinking from Opus, Sonnet, and Haiku, Opus reads Sonnet and Haiku, and Sonnet reads Haiku, but moving down a tier loses the reasoning from above, and moving away from Fable drops its reasoning entirely.

**Jordan:** There are two fancier patterns too, and the guide is cautious about both. The advisor tool, still in beta, lets a cheaper executor ask a stronger model for help mid task, but in one test that bought only one point seven points for about twice the money. Delegating bulk work works better when the job is truly large. An Opus lead running up to twenty five Sonnet workers over about twenty two million tokens of code cost about a third less than Opus alone, and scored about the same. Skip that pattern for a single chain of steps, though, because the planning and merging cost more than they save.

**Alex:** Before we close, a few compatibility warnings, because you cannot always just change the model name. Opus and Fable always think, and turning thinking off returns an error. Forced tool use returns a four hundred error on Sonnet, Opus, and Fable, so use auto, mark the tool strict, and say in the prompt when to use it. Migrating from Haiku four point five means replacing budget tokens with an effort level, and dropping non default sampling values.

**Jordan:** So how do you actually decide? Pull a sample of your real tasks, write an outcome check for each one, run each candidate model at two or three effort levels in its own session, and record the cost per completed task. Plot score against spend, and keep a multi model setup only if it beats every single model point on that chart.

**Alex:** That is the message underneath the pricing tables. Start on Opus at medium, use effort as your first dial, move down for scoped and high volume work, move up only for the genuinely hardest work, let cheaper models do the reading while the expensive model decides, and measure on your own work instead of trusting benchmarks alone.
