**Jordan:** The three jobs were the kind of ordinary work every team knows well. One was hunting a flaky test, one was bringing out of date documentation back in line with the code, and one was switching a simple logger over to structured output.

**Jordan:** My favorite detail is what happened with that flaky test. The problem turned out to be a race in a cache, where the same value could be loaded twice if a second request arrived while the first load was still running.

**Alex:** And the fix was to remember the work already in progress, rather than starting it again, and then to prove the fix by running the whole test suite forty times in a row with zero failures.

**Jordan:** That word prove is doing a lot of work here. In the cloud, asking for thorough proof is cheap for you, because the repeated runs are not tying up the machine you are trying to work on.

**Jordan:** And the logger job is a nice honesty check. Its own testing ran into that same flaky cache problem, it recognized the likely cause, and it said plainly in its summary that the overall suite was not yet clean, instead of pretending everything was green.

**Alex:** That is the trade off of true isolation. Each session only sees its own copy, so one session will not automatically benefit from a fix another session is making at the same moment.

**Jordan:** Which is why the guide suggests splitting parallel work along clear file boundaries, and merging the resulting branches in a sensible order afterwards.

**Alex:** Let us talk about the security model, because that is where a lot of developers will pause before trying this. Your GitHub token does not go into the virtual machine.

**Jordan:** Instead, a proxy outside the machine holds that token, and the session itself only gets a short lived credential that can push to its own working branch.

**Alex:** The repository's own instructions travel with the code, things like the project guidance file, its rules, and its commands. Your personal settings folder on your laptop does not travel.

**Jordan:** And you also control how much network the machine can reach. You can narrow that right down, allow the common package sources and code hosts, or open it up only when a task truly needs the wider internet.

**Alex:** There is one more practical warning hidden in there. Idle machines get reclaimed, so if a session sits for a long time, you may come back to a fresh machine with the conversation restored, which means you should commit work you care about as you go.

**Jordan:** So when should you stay local? The guide is pretty clear that cloud is not a replacement for everything.

**Alex:** Stay local when the job needs something only your machine has, like a database with real local data, a service you can only reach over a virtual private network, a graphics processor, a phone simulator, or hardware sitting on your desk.

**Jordan:** Stay local also for those tight visual loops, where you want to see every change in your own browser within seconds. Cloud is better when the work can be described clearly, checked with a command, and left to run.

**Jordan:** The second is letting the machine prove a fix, whether that is running a suite hundreds of times, or working through a long, slow set of integration tests you would never want to babysit.

**Alex:** A third pattern I like is planning at your desk, building in the cloud, and finishing in your terminal. You agree the plan together where conversation is cheap, save that plan in the repository, and then hand the execution off.

**Alex:** The last big idea is giving a session a way to check its own work. A session that can run your tests, start your server, and try real examples will hand back work that has actually been exercised.

**Alex:** And it reminds you to write the important commands into the repository's own guidance, because your personal notes on your laptop do not reach the cloud machine.
