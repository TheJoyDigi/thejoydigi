**Alex:** Welcome to Anthropic Blogcast. Today we are talking about how Anthropic hardened the launch of Claude Docs. Across two billion requests, the service saw only sixty server errors, and it never had to roll back.

**Jordan:** That is remarkable when you hear where it started. Three weeks before Claude Docs opened to the public, it was a proof of concept on a single node, used by a few thousand people inside Anthropic. They launched on September sixteenth, and by September twenty second, people had created more than four point six million docs, all on about fifty memory optimized pods.

**Alex:** The author, Vivek Nair, says two decisions got them there. First, a chaos loop at launch scale, where Claude ran constantly for two weeks trying to break the service. Second, making the service legible to Claude, so Claude could trace every telemetry signal to a bug or a design decision.

**Jordan:** Let us start with the chaos loop. On September fourth, about two weeks before launch, Claude drove a staging cluster that mirrored production, at more than a million synthetic docs a day, and broke core components on purpose.

**Alex:** The loop was a session in Claude Code left running. It would pick a scenario, run the harness, read the telemetry, propose a fix, ship it to staging, and repeat. That session acted as a coordinator and handed work to sub agents, usually about eleven at a time, and thirty at the peak.

**Jordan:** The scenarios were deliberately paranoid. Ten million new docs created in a single day. Twenty two thousand live connections reconnecting at once. One hot doc with hundreds of viewers, a server killed while it was still loading a doc, and the database stalling, all together.

**Alex:** Each iteration, the harness pushed a feature like document creation to saturation. Claude read telemetry using the Datadog Model Context Protocol server, and came back with a short menu of options and a recommendation. Every database query reported its name and how many rows it scanned compared with how many it returned, so Claude could spot a bad query and rewrite it.

**Jordan:** If a fix was easy to undo, Claude wrote it, deployed it to staging, and reran the test. Anything hard to undo, like changing the database schema, the key layout, or how a doc is stored, needed the author approval first. Claude stopped, asked, and usually brought a recommendation he ended up approving.

**Alex:** Through it all, Claude had to hold two invariants. Docs had to open almost instantly, even ones with a long history. And once the server acknowledged an edit, tests had to show the edit was still there. No confirmed edit could be lost.

**Jordan:** That brings us to legibility. Claude could only close the loop if the system produced accurate telemetry every iteration. So on each iteration, Claude read the telemetry and added whatever it thought was missing. Writing telemetry by hand is tedious, so normally it only goes in after something breaks. Here Claude wrote it as it went.

**Alex:** Memory is the best example. Early on, one large doc was using about three gigabytes on its pod. Claude first tried shrinking one of their caches, but the next run showed the memory was actually in a separate cache inside a dependency, so Claude dropped that change.

**Jordan:** Then Claude kept narrowing it down with finer grained profiling, and found that every keystroke was copying the doc into several different data structures, adding a few megabytes each time. Claude switched those structures to copy on write, so they share one reference instead of each holding its own copy.

**Alex:** After about three days, that doc topped out around one hundred eighty megabytes, and the launch estimate dropped from more than five hundred memory optimized pods to about fifty. That is the payoff of a clean signal.

**Jordan:** The technology choices helped too. The service was written in Rust, with dependencies kept to a minimum, and the few they needed were vendored so the team could read and measure that code themselves.

**Alex:** Rust mattered because it has no garbage collector. All of a doc memory sits in structures the team defined, so when memory grew, Claude could point to the one responsible, change it, and see whether memory came down. The author says a garbage collector would add noise, because memory and latency shift on the collector schedule. He also notes they have great Go tooling too, and did not do a bake off, this is just their experience.

**Jordan:** And Rust being hard for people to write matters less now, because Claude writes it fine. So what happened at launch?

**Alex:** The service held. The first million docs showed up in about thirty hours. They rolled production six hundred twenty nine times in September and never rolled back. Seven of the ten scenarios rehearsed on staging actually happened in production, and by then Claude had shipped most fixes behind runtime flags, so the team usually just flipped a flag.

**Jordan:** Why does this work now, when it might not have a few months ago? Older models could read telemetry, but ten or twenty iterations into a long loop they would forget what they were optimizing for. The author calls that goal drift, a term other Anthropic employees use too.

**Alex:** He used an internal research model roughly comparable to Claude Fable five point two. Claude held the invariants across many compactions, and he never had to repeat them. He also notes Vercel made Turborepo up to ninety six percent faster with a similar supervised agent loop.

**Jordan:** Now the cost, because the author is transparent about it. At the Fable five point two application programming interface list price, as of November twenty twenty six, he used roughly one hundred twenty five thousand dollars of inference from the end of August to launch day. Most went to reading telemetry, writing proposals, generating fixes, and reviewing code.

**Alex:** He guesses work on this scale would once have taken a team of engineers about six months. He also says a good chunk went to infrastructure that only makes sense at this scale, and he burned tokens figuring out the process, so knowing what he knows now, they could have spent about half as much.

**Jordan:** For a smaller team, he estimates a two week push at three thousand to ten thousand dollars, for a stack with a couple of reasonably sized Kubernetes nodes and a Postgres instance. He is clear he has not actually run that version, so it is only a rough sense.

**Alex:** If you want to try it, he gives five steps. First, give Claude access to your telemetry, most observability providers have a Model Context Protocol server Claude can use. Second, have Claude write a load script that throws ten times your real traffic at staging and breaks things on purpose, killing an instance, stalling the database, and deploying in the middle of a spike are good places to start.

**Jordan:** Third, pick a stack Claude can measure most easily, for them that was Rust and few dependencies. Fourth, write down your most important technical invariants before you start and give them to Claude. Fifth, for anything hard to undo, have Claude stop and give you options with a clear recommendation.

**Alex:** The takeaway is not just that Claude can load test. The loop works when you give the model a harness that reproduces failure, telemetry clean enough to trace every number to your own code, and invariants it must hold for weeks, while a person keeps the irreversible calls.

**Jordan:** That combination turned a single node proof of concept into a service that handled billions of requests with only sixty server errors. If you are building something that has to survive its first big week, steal this pattern, start small on staging, and write your invariants down first.
