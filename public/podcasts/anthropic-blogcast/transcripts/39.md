**Alex:** Welcome back to Anthropic Blogcast. Today we are digging into a developer post from Claude dot dev called How the Claude Code Team Thinks About Verification, published on November sixteenth, twenty twenty six. And Jordan, the opening stat stopped me cold. On the Claude Code team, about ninety percent of the code is now written and reviewed by Claude itself.

**Jordan:** Ninety percent is exactly why this matters. When agents write most of the code, the bottleneck is no longer typing. It is trust. How do you know the work is actually good, without a human reading every single line?

**Alex:** Their answer is verification loops. Give the agent a way to check its own work with real evidence, and you can delegate far more. Without a loop, you can really only run one or two Claudes at a time, because you have to check everything yourself. With a loop, you can run dozens or even hundreds in parallel.

**Jordan:** They even put a number on the quality gain. In internal testing around structured file generation, having a separate grader check Claude's work against a rubric improved task success by up to ten points over a standard prompting loop, and the largest gains were on the hardest problems.

**Alex:** What used to be expensive to verify, things like tests, benchmarks, specs, and real end to end runs, is now cheap to ask an agent to create. And once those tests exist as software, they can run again and again without burning many extra tokens. If an agent keeps failing the same check, you can also turn that lesson into a hook or a rule in your CLAUDE dot MD file, so it mostly stops happening again.

**Jordan:** But the post warns that not all tests are created equal. If your tests are flaky, you will train the agent to just run them again instead of fixing the code. If your tests are slow, the agent will run fewer of them, which makes it harder to pinpoint what broke. So they name three test types most worth investing in.

**Alex:** First, and they say if you pick only one, pick this one, end to end tests. Those describe real user flows, like adding an item to a cart, checking out, and landing on a confirmation page. They are hard to fool. Either the whole feature works or it does not, and they give you definitive done criteria.

**Jordan:** A unit test failure might just say error, timeout after thirty seconds, and you are shooting blind. An end to end failure can show a step by step trace, a screenshot, and a plain description, like the place order button stayed disabled because the payment form never loaded. You can pass every unit test and still break the feature, because neither the agent nor the unit test understood the full task.

**Alex:** So they recommend giving your agent hands and eyes on the real running system, using tools like the Chrome DevTools Protocol, simulators, or an API harness, guided by a feature map that lists paths, keyboard shortcuts, selectors, and expected results from the user's point of view.

**Jordan:** The second type is property tests. Most tests check what you thought might go wrong. Property tests hunt for the edge cases people tend to miss, which is exactly where agents often fail. You start with a statement you believe can never fail, and a library generates thousands of inputs trying to prove you wrong. For JavaScript and TypeScript that might be fast-check, for Python it is Hypothesis, and for Rust it is proptest.

**Alex:** And the classic properties show up in almost every project. Round trip encoding, if you encode something and then decode it, you get the original back. Invariants, like an account balance can never become negative. Idempotency, doing a migration or a retry twice has the same effect as doing it once. And equivalence, optimized code produces the same result as the naive but correct version. Because the inputs are not created with the same bias as the code, property tests keep agents honest, and they help a lot on rewrites when the spec has drifted from production.

**Jordan:** Third is differential tests, where the old system is the oracle. These shine for large scale migrations where behavior should stay the same. You run the old and new systems on the same inputs and compare outputs. If they differ, you have found a bug or a breaking change. Use randomly generated inputs or a sample of real production traffic, normalize away irrelevant differences like whitespace, and keep a list of approved changes where the new system should intentionally differ.

**Alex:** Now the second half is how the team runs this day to day, and their first rule is blunt. Verification means running the change. Running the app end to end matters more than tests alone. You would not ship an iPhone change without trying it in a simulator, and the same goes for Claude. For web changes Claude uses the Chrome extension, for mobile an iOS or Android MCP server, for desktop computer use, and for backend work it runs the service locally.

**Jordan:** To make that repeatable, they codify it in a skill called verify, stored in a dot Claude skills folder in the repo, as close to the relevant code as possible. They invest in making that verify skill fast and reliable, asking Claude to iterate on it and stress test it. When Claude can smoke test its own changes, it catches real mistakes faster, much more like a human would.

**Alex:** A few more rules stood out. Claude runs the checks and tries to fix failures itself, but if a check is still failing after three rounds, it stops and brings in a human. Code owners write their own checks and refine them until they flag what the owner would flag, and when a check pulls in a reviewer, it should explain why.

**Jordan:** Then there is their reliability checklist. Thirty nine items, each with a trigger you can read from a diff, a check, and the incidents behind it. One example is around resuming old transcripts. When session storage changes, they ask whether a new field loads safely, because older transcripts will not have it. Claude reads the diff and checks only the matching items, usually three to ten, so nobody has to memorize past outages.

**Alex:** They also do not stack more reviewers to get better reviews. Adding a second, more expensive reviewer is often worse than tuning the primary one. They use a REVIEW dot MD file that says what the reviewer should pay attention to, and each round builds on earlier rounds and past failures instead of starting from scratch.

**Jordan:** And a critical integrity rule. Changes cannot modify their own checks. Code Review reads the REVIEW dot MD file from the base branch, never from the pull request's own changes. Reviews are tied to specific commits, because a passing review on an out of date commit means nothing, and cheap checks, tests, build, and linter, run before a pull request is even opened.

**Alex:** They start any new gate in observe mode too. Every commit gets stamped with how it was verified, even if the stamp says none, so they can query for unverified commits. A new gate logs what would have been blocked first, so they can catch false positives, before it starts enforcing. And they test their checks against what actually mattered, past incidents and reverts, recreating the repo at the time of review with a one sentence answer key for the bug. Only findings that correctly describe that bug get points, and clean changes act as a control against over flagging.

**Jordan:** Finally, turn misses into rules. A pattern from human reviews or reverts has to occur in at least two pull requests and be identifiable from a diff before it becomes a candidate rule. Three agents try to disprove it, and a human approves it. Flaky tests get tough treatment too. Claude cannot skip them, add sleeps, or retry until they pass. If it cannot find the root cause, it deletes the test and writes down why. And all these rules need regular pruning, or they just keep growing.

**Alex:** So the closing message is the one I would put on a wall. Treat your verification layer like any other system. Keep it out of reach of the changes it judges, grade it against the bugs that actually mattered, write down lessons when it misses, and prune those lessons so they stay worth running.

**Jordan:** Do that, and your job shifts. You stop reading every diff, and you start defining what done looks like and reviewing the evidence. That shift is what lets you run many Claudes at once, with confidence. Thanks for listening to Anthropic Blogcast. We will be back with the next post from Anthropic and Claude dot dev.
