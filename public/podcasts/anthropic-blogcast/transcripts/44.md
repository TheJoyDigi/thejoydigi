**Alex:** Welcome to Anthropic Blogcast. Today we are digging into a developer guide from the Claude dot dev blog called A practical guide to shipping with Claude Code, written by Addy Osmani and published on November twenty-fourth, twenty twenty-six.

**Jordan:** And the big idea is that opening a pull request is not the finish line. It is more like the halfway point, right?

**Alex:** Exactly. After you open a pull request, there is a pile of follow-up work. Continuous integration fails. A review comes back with six comments. A merge from the main branch creates a conflict. Each task is tiny on its own, but every one pulls you out of your focus work. On the Claude Code team, an agent commonly does that follow-up work. It can pick up an issue a reviewer found, so when the author comes back, the pull request has already been updated once.

**Jordan:** So the guide is about setting up your own repository to work that way?

**Alex:** Yes, using new functionality that arrived with the Claude Ship launch. It is written for a developer or tech lead whose team works on GitHub and who does not have admin privileges. You can start on your own, right now, with a few commands, and admins only get involved if the team wants agents doing this automatically on everyone's pull requests. And you are still the architect. You define what to build, how to build it, and what the bar for merging is.

**Jordan:** What is Claude Ship, exactly?

**Alex:** It is three agents that tackle the post pull request process, finding issues, addressing issues, and deciding whether a change can merge. Code Review is generally available, while P R Steward and Claude Approvals are both in beta. There is also a slash ship command you run yourself in Claude Code to try it on your own pull requests, and it works even before an admin has turned on any of the agents.

**Jordan:** Where do you start if you only do one thing?

**Alex:** The guide says, review your branch before you push it. Run slash code-review at the Claude Code prompt. It reviews the commits on your branch and your uncommitted changes for correctness bugs, so they are less likely to come back as review comments or failed checks later. You can add an effort level and a pull request number, use dash dash fix to apply the findings to your working tree, or dash dash comment to post them on the pull request. The effort scale goes from low to max. At low you only see the findings it is most sure about, and higher levels show more, including findings it is less sure about.

**Jordan:** Any caveats there?

**Alex:** Two. Slash code-review ultra runs a deeper review in the cloud, needs a login at Claude dot A I, and can be billed separately from your plan. And edits made by the fix option during a background review may not be caught by the rewind feature, so commit first if you want an easy way back.

**Jordan:** Then the main event, slash ship. What does it actually do?

**Alex:** If there is no pull request for your branch yet, it does four things. First, it commits your pending changes, behaving as if you had run git add dash A, so it respects your git ignore file, and you are notified before the commit and can abort by hitting Escape. Second, it pushes and creates the pull request as you. Third, it performs a code review and fixes the issues it judges to be valid. Fourth, it watches the pull request for up to seven days, working on failing checks, conflicts, and review comments, and exits if the pull request is merged or closed.

**Jordan:** That commit step sounds like the one that could surprise people.

**Alex:** The guide flags exactly that. Run git status first. There are also safety limits. The command will not commit files with names that look like secrets, or files that set the rules, like C L A U D E dot M D, Review dot M D, or anything in the dot Claude or dot GitHub directories. Those you commit manually. And in a public repository, it will not commit changes for you at all.

**Jordan:** What about the watch itself? How does it run?

**Alex:** Claude watches the pull request as you, on your machine, using your quota, so closing your laptop stops it. You need to be logged in to the GitHub command line tool, it only watches a pull request you opened, and it will not watch in bypass permissions mode. On Windows, slash ship opens the pull request and reviews it, but the watch does not start. The watch also uses model turns while you are away, so it counts against your plan usage or your A P I bill.

**Jordan:** That raises the trust question. It is running commands on my machine.

**Alex:** The guide is blunt. Only run the watch on a repository where you trust everyone who can land changes on the base branch, because the watch merges that branch into yours and runs commands like your tests. There are guardrails. Claude is told never to merge the pull request, the git and GitHub commands it can run unattended are constrained, and its own commits leave out the rule setting files. But its commits also skip your local git hooks, so any check that really matters belongs in continuous integration and branch rules.

**Jordan:** And if I already have a pull request open?

**Alex:** Use slash steward. You check out the branch and run it, optionally with a pull request number, and it runs just the watch component, without reviewing first. Do not confuse it with P R Steward, the team service that runs as the Claude bot in the cloud. The local command runs as you. You stop either watch with slash ship stop or slash steward stop.

**Jordan:** What happens when Claude hits something big?

**Alex:** It escalates. It makes small changes and elevates bigger ones, like a request to redesign something, a new A P I, or a security issue it could not resolve. It also pushes at most three times for a given issue, then reports back the solutions it attempted. If the same check keeps failing after three rounds, the approach is probably wrong, and that is the moment to hand it back to the author.

**Jordan:** Now the part I like. How do one-off fixes become team knowledge?

**Alex:** Patterns repeat. The same comment from the same reviewer, a setup instruction Claude has to figure out every time, a flaky check. You write them down in different files depending on which tool reads them. Conventions code should follow go in C L A U D E dot M D, read by Claude Code, the local review, Code Review, and P R Steward. Rules about how pull requests get reviewed go in Review dot M D, which Code Review and P R Steward read, but the local review does not. How to start and exercise the app goes in a verify skill file, and how pull requests should be looked after goes in a steward skill file.

**Jordan:** Give me a concrete example.

**Alex:** Say a peer asks you twice to make sure a new query contains a tenant check. That becomes a line under always check in Review dot M D. The guide's example also says style and naming are a nit at most, asks for at most five nits, and says skip generated files and lock files. And there is a bar for this. A pattern has to repeat on at least two pull requests before it becomes a rule, a person approves the pull request that adds it, and you should delete rules as needed, not just accumulate them.

**Jordan:** Last big section. How does a whole team adopt this?

**Alex:** Five steps. Agree on budget constraints ahead of time. Protect the default branch, requiring an approval on the latest push. Have an owner in your Claude organization enable Code Review, then enable P R Steward in manual mode, so it kicks in when someone comments at Claude steward. And create an approvals policy in observe mode.

**Jordan:** How does that approvals policy work?

**Alex:** Claude Approvals reads a file called approvals dot y m l in the dot Claude folder on the default branch. A simple first policy says a change takes two people, with Claude set to comment rather than approve, and a line naming Code Review as advisory. Seats is the number of people who have to approve, and the author can take one seat. If more than one rule matches, the strictest wins. In observe mode, the check only tells you what it would have decided.

**Jordan:** And there were two warnings there.

**Alex:** Yes. Do not drop the advisory line, because once the policy file is on the default branch, Code Review only kicks off automatically on pull requests matching a rule that names it. Without it, your automatic reviews stop. And a policy naming Code Review can start billed reviews, even in observe mode, so tell the budget owner before you merge it. You then monitor observe mode for a week or two, compare its decisions with your reviewers, and only then remove observe mode to enforce. The guide also stresses that Claude's approvals count as real approvals on GitHub, so read your policy and your branch rules together.
